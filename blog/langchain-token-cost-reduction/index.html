I run a LangChain agent that generates weekly market summaries. Same chain, same tools, slightly different inputs each week. After three months I looked at my Anthropic bill and realized I had been paying full price every single run — for reasoning my agent had already done dozens of times.

The problem is structural: LangChain is stateless by default. Every llm.invoke() call starts from zero. Your chain has no memory of what it produced last Tuesday, or last month. Every run is as expensive as the first.

Where the money goes

Most LangChain cost waste comes from recurring patterns:

  • Agents that run on a schedule (daily digests, weekly reports, recurring audits)
  • Chains that handle structurally similar queries (same intent, different specifics)
  • Multi-step chains where early reasoning steps are nearly identical across runs
  • RAG pipelines that re-synthesize over the same documents

The more repetition in your workload, the more you're overpaying.

Why LangChain's built-in caching isn't enough

LangChain has a set_llm_cache function that caches exact string matches. It's useful but limited:

  • Requires exact input match — one word difference misses the cache entirely
  • Doesn't understand semantic similarity ("weekly report for Acme" vs "Acme Corp weekly summary")
  • Doesn't persist learning about what failed or succeeded across sessions
  • No cost or token tracking

Prompt caching from Anthropic and OpenAI helps with repeated prefixes — but when your chain re-derives reasoning with slightly varied inputs, it doesn't fire.

Execution-level caching

Mnemon operates one level higher — it caches the execution plan, not the prompt. It intercepts BaseChatModel.invoke() before it reaches the LLM and checks if this problem has been solved before.

No chain restructuring. No wrapper classes. Your existing code stays exactly as-is.

How matching works

System 1 — Exact match: SHA-256 fingerprint of the full input. Identical input on a repeat call returns the cached result in ~2.66ms. Zero tokens, zero API cost.

System 2 — Semantic match: Similar but not identical inputs ("Acme Corp weekly report" vs "weekly report for Acme") are matched against stored executions. Only the parts that actually changed get regenerated. You pay for the delta.

System 2 requires embeddings: pip install mnemon-ai[full] or set an OpenAI/Anthropic API key. Without it, Mnemon runs System 1 only — still valuable for exact repeats.

Full explicit control

For workloads where you want precise cache boundaries:

import mnemon
from langchain_anthropic import ChatAnthropic

m = mnemon.init()
llm = ChatAnthropic(model="claude-sonnet-4-6")

def generate_report(goal, inputs, *_):
    return llm.invoke(f"{goal} for {inputs['client']}").content

result = m.run(
    goal="weekly fintech market summary",
    inputs={"client": "Acme Corp", "week": "May 26"},
    generation_fn=generate_report,
)

print(result["output"])           # your report
print(result["cache_level"])      # "system1" | "system2" | "miss"
print(result["tokens_saved"])     # tokens saved this run
print(result["latency_saved_ms"]) # ms saved this run

What it doesn't help with

  • Chains where every input is genuinely unique
  • Real-time queries where freshness is required
  • Cold starts — first execution of any goal still hits the LLM
